# 발행 절차

글이 주제 후보에서 공개 글이 되기까지의 단계와 LinkedIn 운영 방식을 정한다.
블로그가 정본이고 LinkedIn은 확산과 교류를 위한 채널이다.

## 상태

| 상태 | 뜻 | 다음으로 넘기는 사람 |
|---|---|---|
| `idea` | 주제 후보. 근거 자료가 아직 모이지 않음 | 사용자 |
| `draft` | 초안 작성 중. 브랜치에만 있음 | 작성 에이전트 또는 사용자 |
| `review` | 정확성과 공개 가능 여부 검토 중. PR 열림 | 검토자 |
| `approved` | 사용자가 발행을 승인함 | 사용자 |
| `published` | `main`에 병합되어 배포됨 | — |

- 상태는 PR과 글의 front matter에 적는다. Linear 연동이 구현되면 Linear가 정본이 된다.
- `review`에서 `approved`로 넘기는 일은 사용자만 한다.

## 단계

| 번호 | 단계 | 지금 가능한 방식 |
|---|---|---|
| 1 | 정보·아이디어 수집 (Deck) | 수동. 레포와 연동 없음 |
| 2 | 관련 지식 조회 (Notion, LLMWiki) | 수동. 레포와 연동 없음 |
| 3 | 근거 자료 확인 (Google Drive) | 수동 |
| 4 | 주제 선정 | 사용자 결정 |
| 5 | 작업 등록 (Linear) | 사용자 승인 후 수동 등록 |
| 6 | 초안 작성 | 에이전트가 `post/<slug>` 브랜치에 작성 |
| 7 | 근거·정확성·공개 가능 여부 검토 | `AGENTS.md`의 공개 전 점검 |
| 8 | 사용자 승인 | PR 리뷰 |
| 9 | 레포 반영 | PR 병합 (사용자) |
| 10 | 빌드와 미리보기 | 로컬 빌드, PR 워크플로의 빌드·링크 검사 |
| 11 | 배포 | `main` 병합 시 자동 |
| 12 | LinkedIn 초안 | 에이전트가 PR 설명이나 비공개 작업 공간에 작성 |
| 13 | LinkedIn 발행 | 사용자가 직접 게시 |
| 14 | 결과 기록 | 공개 URL과 날짜를 Linear 또는 작업 기록에 남김 |

"수동"이라고 적힌 단계는 자동 연동이 없다는 뜻이다. 연동을 구현하면 이 표를 먼저 고친다.

## 에이전트가 넘겨받는 것과 넘겨주는 것

초안 작성을 맡은 에이전트는 다음을 받아야 시작한다.

- 주제와 글 유형, 콘텐츠 축
- 사용자가 승인한 근거 자료의 목록
- 공개해서는 안 되는 범위

초안과 함께 다음을 넘긴다.

- 문장별 출처 대응표. 출처를 찾지 못한 문장은 표시한다.
- 공개 전 점검 아홉 항목의 결과
- 사용자가 확인해야 할 질문

Deck, LLMWiki, Notion에 있는 정보를 그대로 공개 글로 옮기지 않는다. 승인된 자료만 근거로 쓴다.

## 발행 주기

아래는 출발점이고 의무가 아니다. 연구 일정과 업무 부담에 맞춰 조정한다.

| 주기 | 할 일 |
|---|---|
| 매주 | 다음에 쓸 주제 후보 고르기 |
| 1~2주 | 글 한 편 발행 |
| 매월 | 프로젝트의 개발 이력과 상태 갱신 |
| 분기 | 대표 프로젝트, 연구 방향, About 갱신 |
| 수시 | 논문 게재 같은 주요 성과 |

발행 횟수보다 글의 질과 꾸준함을 우선한다.
글이나 사이트에 발행 날짜와 주기를 약속하지 않는다.

## 예약 발행

현재 워크플로에는 예약 실행이 없다. 미래 날짜의 글은 그 날짜가 지난 뒤 빌드가 한 번 더 돌아야 공개된다.
날짜를 미리 적어 두는 방식에 기대지 말고, 발행하는 날 병합한다.

## LinkedIn

### 원칙

- LinkedIn 글은 블로그 글의 요약이 아니다. 링크를 누르지 않아도 읽을 가치가 있어야 한다.
- 기술적 질문이나 구체적인 경험으로 시작한다.
- 성과를 부풀리지 않는다. 결과에는 조건을 붙인다.
- 협업자와 소속 기관의 기여를 적는다. 이름을 밝힐 때는 당사자의 동의를 확인한다.
- 해시태그는 관련 있는 것으로 3~5개만 쓴다.
- 반응을 끌어내려는 문장을 넣지 않는다.
- 게시는 사용자가 직접 한다. 에이전트는 초안만 만든다.

### 유형

| 유형 | 시작 | 본문 | 맺음 |
|---|---|---|---|
| Technical Insight | 기술적 질문 | 문제의 배경, 발견한 것, 그것이 뜻하는 바 | 블로그 글 연결 |
| Project Update | 이번에 한 일 | 푼 문제, 현재 결과와 조건, 한계 | 다음에 할 일 |
| Research Reflection | 겪은 일 | 고민과 배운 점 | 더 알고 싶은 문제 |
| Milestone | 사실 한 문장 | 맥락, 함께한 사람과 기관 | 관련 자료 연결 |

### 정해야 할 것

아래 두 가지는 몇 차례 운영해 본 뒤 사용자가 정한다. 어느 쪽이 더 많이 노출되는지에 대해서는 근거 없이 단정하지 않는다.

| 항목 | 선택지 |
|---|---|
| 언어 | 한국어 본문 뒤에 영어 본문을 붙이는 방식 / 영어만 쓰는 방식 |
| 블로그 링크 위치 | 본문 끝 / 첫 댓글 |

### 첨부 자료

- 글마다 그림이나 짧은 영상 하나를 붙인다. 블로그 글의 대표 그림을 쓴다.
- 환자 정보와 회사 내부 화면이 보이는 자료는 쓰지 않는다.
- 블로그 글에는 공유용 대표 이미지를 지정한다. 지정하지 않으면 링크 미리보기에 그림이 나오지 않는다.

## 발행한 뒤

- 공개 URL이 열리는지, 그림과 수식이 제대로 보이는지 확인한다.
- 오류를 고칠 때는 글 끝에 수정 날짜와 내용을 한 줄로 남긴다. 조용히 바꾸지 않는다.
- 발행된 글의 URL은 바꾸지 않는다. 바꿔야 하면 옛 주소에서 새 주소로 넘어가게 한다.
